# TechNote — M365 · Power Platform · Development 블로그

GitHub Pages에 바로 올릴 수 있는 정적 기술 블로그입니다. 밝고 정돈된 디자인,
카테고리 트리 + 태그, 상단 실시간 검색, 검색엔진 최적화(SEO), **한글/영문 전체
번역(우측 상단 언어 토글)**을 갖췄고, 글이 수백~수천 개로 늘어나도 목록 페이지가
무거워지지 않도록 **메타데이터와 본문을 분리해서 관리**하며 목록도 한 번에 12개씩만
그리고 나머지는 스크롤에 따라 자동으로 더 불러옵니다(자세한 이유는 아래 "데이터
구조"·"다국어"·"목록 페이지네이션" 참고).

## 파일 구조

```
blog/
  index.html          # 메인: 글 목록 + 검색 + 카테고리/태그 필터
  post.html           # 개별 글 보기 (post.html?id=글아이디)
  assets/
    style.css         # 밝은 테마 디자인
    app.js            # 목록/검색/글 렌더링 + SEO(JSON-LD) + 본문 지연 로드
    img/<주제>/        # 글에 쓰는 이미지(실습 캡처 등) 저장 위치
  data/
    index.js          # ★ 모든 글의 메타데이터 단일 소스 (제목/요약/태그 등, 본문 제외)
    index.json         # 같은 데이터의 JSON 미러(참고용)
    posts/
      <글아이디>.js     # 글 하나의 본문만 담은 파일 (그 글을 열 때만 로드됨)
      <글아이디>.json    # 같은 본문의 JSON 미러(참고용)
  add_post.py         # 링크·내용을 받아 index.js + posts/<id>.js에 글 추가 (자동 업로드의 핵심)
  README.md
```

## 데이터 구조 — 왜 메타데이터와 본문을 나눴나

처음엔 글 전체(본문 포함)를 `data/posts.js` 파일 하나에 다 넣었습니다. 글이 몇 개
안 될 때는 문제없지만, 이 방식은 **글이 늘어날수록 목록 페이지(index.html)가 매번
모든 글의 본문 전체를 다운로드**하게 됩니다 — 방문자가 글 하나만 읽어도 브라우저는
글 수백~수천 개의 본문 HTML을 전부 받아온 뒤라는 뜻입니다. 이미지가 많은 글이
섞이기 시작하면 더 심해집니다.

그래서 지금은 두 층으로 나눕니다.

- **`data/index.js`** — 모든 글의 메타데이터(제목, 요약, 태그, 카테고리, 날짜, 출처,
  예상 읽기 시간)만 담습니다. 본문은 들어있지 않아서 글이 수천 개가 되어도 이 파일은
  완만하게만 커집니다(글 1개당 대략 0.5~1KB 수준). 목록/검색/태그 필터는 이 파일
  하나만 읽습니다.
- **`data/posts/<글아이디>.js`** — 글 하나의 본문 HTML만 담은 파일입니다. `post.html`이
  그 글을 열 때(`<script src>` 태그를 동적으로 추가하는 방식) 그 글의 파일 하나만
  불러옵니다. 다른 글의 본문은 전혀 내려받지 않습니다.

이 구조 덕분에 글이 아무리 늘어나도 목록 페이지의 로딩 속도는 거의 변하지 않습니다.
다만 **사이트 내 검색은 제목·요약·태그·카테고리명까지만** 대상으로 합니다(본문 전체
검색은 목록 페이지에 본문을 올려야 해서 이 구조와 상충합니다). 나중에 글이 정말
많아져서 `index.js` 자체도 무거워지면(대략 수천 개 이상), 카테고리별로
`data/index-m365.js`처럼 인덱스를 더 쪼개거나, 본문 전체 검색이 꼭 필요해지면
[Pagefind](https://pagefind.app/) 같은 정적 검색 인덱스 생성기를 빌드 단계에 추가하는
방향을 권장합니다.

`.json` 파일들은 브라우저가 실제로 쓰는 건 아니고(브라우저는 `.js`만 읽습니다),
서버 환경에서 `fetch()`로 읽는 폴백 경로와 스크립트로 데이터를 다룰 때 참고용
미러입니다.

### 다국어 필드 형식

`title`, `summary`, `tags`(index.js)와 `content`(posts/<id>.js)는 모두 언어별로
값이 다르기 때문에 `{ "ko": "...", "en": "..." }` 형태의 객체로 저장합니다(아래
"다국어(한글/영문)" 섹션 참고). `category` 이름, `site.author`처럼 두 언어에서 값이
같은 필드는 그냥 문자열 그대로 둡니다 — `app.js`의 `pick(value, lang)` 헬퍼가 객체면
현재 언어 값을, 문자열이면 그 값을 그대로 반환하므로 섞여 있어도 문제없습니다.

## 미리보기 (내 PC에서)

`index.html` 을 그냥 더블클릭해도 열립니다 (데이터를 JS로 넣어 서버 없이 동작).
혹시 브라우저 보안설정으로 안 열리면 폴더에서 아래를 실행하고
`http://localhost:8000` 접속하세요:

```
python -m http.server 8000
```

## GitHub Pages 배포

1. GitHub에 새 저장소 생성 (예: `technote`)
2. 이 `blog/` 폴더의 내용을 저장소 루트에 업로드(또는 `git push`)
3. 저장소 **Settings → Pages → Source** 를 `main` 브랜치 `/ (root)` 로 설정
4. 몇 분 뒤 `https://<사용자명>.github.io/technote/` 에서 공개됩니다
5. `data/index.js` 의 `site.baseUrl` 을 이 주소로 바꿔주세요(SEO/공유용)

## 글 추가하는 법

**모든 글은 한글판과 영문판을 함께 만듭니다.** title/summary/tags/content 전부
`--*-ko` / `--*-en` 두 벌을 넘겨야 하고(아래 "다국어(한글/영문)" 참고), 기존 글을
수정할 때도 두 언어를 같이 반영합니다.

### 방법 1: 스크립트 (자동화에 적합, 새 글 추가 전용)

```
python add_post.py \
  --title-ko "제목" --title-en "Title" \
  --category powerplatform \
  --tags-ko "Power Automate,자동화" --tags-en "Power Automate,Automation" \
  --source youtube --url "https://youtube.com/..." \
  --summary-ko "한 줄 요약" --summary-en "One-line summary" \
  --content-ko "<p>본문 HTML</p>" --content-en "<p>Body HTML</p>"
```

- `--category` : `m365` | `powerplatform` | `dev`
- `--source`   : `original`(직접작성) | `blog` | `youtube` | `article` | `notion`
- 실행하면 `data/index.js` 맨 앞에 글 메타데이터가 추가되고, `data/posts/<id>.js`에
  본문이 별도로 저장되며, `site.version`이 1 증가하고 `site.lastUpdated`가 오늘
  날짜로 갱신됩니다(아래 "버전 표시" 참고). 커밋/푸시하면 사이트에 반영.
- `add_post.py`는 **새 글 추가 전용**입니다 — 기존 글을 수정하는 기능은 없으므로,
  이미 있는 글의 내용을 고칠 때는 아래 "방법 2"처럼 `data/index.js`의 해당 항목과
  `data/posts/<id>.js`를 직접 편집합니다.

### 방법 2: 직접 편집 (새 글 추가 또는 기존 글 수정)

`data/index.js` 의 `posts` 배열에 메타데이터를 하나 추가하고(`content` 필드는
넣지 않습니다), 같은 `id`로 `data/posts/<id>.js` 파일을 새로 만들어 본문을 넣습니다.
기존 글을 고칠 때는 같은 `id`를 가진 항목/파일을 찾아서 그대로 덮어씁니다.

`data/index.js`에 추가할 메타데이터:
```js
{
  "id": "고유-슬러그",
  "title": { "ko": "제목", "en": "Title" },
  "category": "m365",
  "tags": { "ko": ["태그1", "태그2"], "en": ["Tag1", "Tag2"] },
  "date": "2026-07-27",
  "source": { "type": "article", "url": "https://..." },
  "summary": { "ko": "목록에 보일 한 줄 요약", "en": "One-line summary shown in the list" },
  "readingMinutes": 5
}
```
메타데이터를 추가/수정한 뒤에는 `site.version`을 1 올리고 `site.lastUpdated`를
오늘 날짜로 바꿔줍니다(add_post.py를 쓰면 자동으로 처리됨).

`data/posts/고유-슬러그.js` 에 넣을 본문 파일:
```js
window.BLOG_POST_CONTENT = window.BLOG_POST_CONTENT || {};
window.BLOG_POST_CONTENT["고유-슬러그"] = {
  "ko": "<p>본문은 HTML로. h2, ul, code, pre, blockquote, img, details/summary 지원</p>",
  "en": "<p>Same content in English, same HTML shape.</p>"
};
```

## 다국어(한글/영문)

화면 우측 상단(글 목록 페이지는 검색창 옆, 글 상세 페이지는 "← 목록으로" 옆)에
**한글/EN 토글 버튼**이 있습니다. 클릭하면 그 페이지 전체(제목, 요약, 태그, 본문,
카테고리 "전체" 라벨, 검색창 placeholder, "N개의 글" 문구, 관련 글, 원문 보기
등)가 즉시 해당 언어로 다시 그려집니다. 선택한 언어는 브라우저의 `localStorage`에
저장되어 새로고침하거나 다른 글로 이동해도 유지되고, 글 카드 링크에는
`&lang=ko`/`&lang=en`이 붙어서 상세 페이지도 같은 언어로 열립니다.

- **이후로 내가 "블로그에 글 올려줘"라고 요청하면, 항상 한글판과 영문판을 함께
  만들어서 반영합니다.** 번역이 아니라 같은 내용을 두 언어로 자연스럽게 쓴다는
  느낌으로 작성하되(직역 금지 원칙은 "글쓰기 원칙" 참고), 두 언어의 내용·구성·
  이미지는 동일해야 합니다 — 이미지, `<details>` 토글 개수와 위치, 섹션 구성은
  한글판과 영문판이 완전히 같아야 하고, 텍스트만 그 언어에 맞게 다시 씁니다.
- 새 글은 `add_post.py`(방법 1)로 두 언어를 한 번에 넣거나, 위 "방법 2" 형식으로
  `data/index.js`/`data/posts/<id>.js`를 직접 편집합니다.
- 기존 글 중 아직 영문판이 없는 글은 없습니다 — 8개 글 전부 2026-08-13에
  일괄 번역해 두었습니다. 새로 글을 추가할 때만 두 언어를 같이 챙기면 됩니다.
- 카테고리 이름(Microsoft 365 / Power Platform / Development)처럼 두 언어에서
  표기가 같은 값은 다국어 객체로 만들 필요 없이 문자열 그대로 둬도 됩니다.

## 목록 페이지 로딩 방식 — 더 보기 / 무한 스크롤

글이 많아져도 목록 페이지가 한 번에 다 그려지지 않도록, 처음에는 **12개**만
표시합니다(`assets/app.js`의 `PAGE_SIZE` 상수). 그 아래로는:

- 화면 하단에 "더 보기" 버튼이 나타나고, 누르면 다음 12개가 추가로 그려집니다.
- 동시에 하단까지 스크롤하면 `IntersectionObserver`가 자동으로 다음 12개를 불러오는
  **무한 스크롤**도 함께 동작합니다(버튼과 스크롤 둘 다 같은 로직을 씁니다).
- 카테고리·태그·검색 조건을 바꾸면 표시 개수는 다시 12개로 초기화됩니다.
- 전체 글을 다 보여주면 버튼은 사라지고 "총 N개의 글을 모두 표시했습니다" 안내만
  남습니다.
- 이 방식은 목록(`data/index.js`)을 통째로 메모리에 들고 있다가 화면에 그리는
  개수만 제한하는 것이라, 데이터를 나눠서 불러오는 방식(페이지 URL, API 페이지네이션)은
  아닙니다 — `index.js`가 본문을 포함하지 않아 가벼우므로(위 "데이터 구조" 참고)
  수천 개 규모까지는 이 방식으로 충분합니다. `index.js` 자체가 무거워지는 규모가
  되면(대략 수천 개 이상) 그때 가서 실제 데이터 분할을 검토합니다.

## 버전 표시 — 여러 PC로 나눠 작업할 때 최신 여부 확인

화면 하단 footer에 `v1 (2026-08-13)`처럼 데이터 버전과 마지막 갱신일이 표시됩니다
(`data/index.js`의 `site.version`/`site.lastUpdated`). 글을 추가·수정해서
`data/index.js`가 바뀔 때마다 버전을 1 올리고(`add_post.py`를 쓰면 자동), 이
숫자로 "지금 내가 들고 있는 로컬 사본이 GitHub에 올라간 것보다 낮은 버전은 아닌지"를
화면만 보고 바로 확인할 수 있습니다. 로컬 버전이 GitHub보다 낮으면, 작업을 새로
시작하기 전에 먼저 GitHub의 최신 내용을 받아와 반영합니다.

## 글쓰기 원칙 (항상 지킬 것)

- **모든 글은 한글판·영문판을 함께 만든다.** 자세한 형식과 예시는 위 "다국어
  (한글/영문)" 섹션을 참고한다.
- 본문(특히 도입부)에 "이 영상을 보고", "~를 참고해", "~님의 글을 정리했습니다" 같은
  취재 과정/출처 언급을 절대 넣지 않는다. 마치 처음부터 필자가 직접 아는 내용을
  설명하는 것처럼, 주제 자체로 바로 시작한다.
- 원문을 번역하거나 문장만 살짝 바꾸는 식으로 쓰지 않는다. 내용을 완전히 이해한 뒤
  스스로 구성·문장을 새로 짜서 쓴다.
- 출처는 숨기지 않는다. 다만 노출 위치는 글 맨 끝(자동으로 붙는 "원문 보기" 링크,
  `source.type`/`source.url`)으로만 제한한다. 본문 중간에 출처를 다시 언급하지 않는다.
- 이미지는 원본 영상/게시물에서 캡처하지 않는다. Microsoft Learn 등 공식 문서나
  다른 공개 자료에서 관련 이미지를 찾아 쓰고, 캡션에 출처를 표기한다.
  - 예외: 태그에 `증적`이 붙는 글(사내에서 직접 구성·검증한 실습/증적 자료를
    바탕으로 쓰는 글)은 이미지 규칙이 다르다. 이 경우에는 실습 환경에서 직접
    캡처한 스크린샷과 Microsoft Learn 등 공식 이미지를 함께 사용한다. 내부
    캡처 이미지는 파일을 `assets/img/<글 슬러그 또는 주제>/`에 저장해 상대
    경로로 넣고 캡션에 `(실습 환경 캡처)`라고 표기하며, 공식 이미지는 기존
    방식대로 `(출처: Microsoft Learn)` 등으로 표기한다. 캡처 이미지에 실제
    고객사·실사용자 정보가 보이지 않는지(테스트 테넌트·샘플 계정인지) 넣기
    전에 반드시 확인한다. `증적` 태그가 없는 일반 글에는 이 예외를 적용하지
    않는다.
- 새 글을 쓰기 전에 `data/index.js`의 기존 글 제목·태그·요약을 확인해서, 이미 다룬
  주제와 겹치는 글은 쓰지 않는다. 같은 제품/기능이라도 기존 글이 다루지 않은
  각도(다른 세부 기능, 실무 시나리오, 최신 업데이트 등)라면 겹치는 게 아니다.
- 링크(기사/유튜브)를 따로 주지 않고 "M365 관련 글 써줘"처럼 요청받으면, Microsoft
  Learn·Tech Community·공식 블로그 등을 직접 찾아 조사한 뒤 위 원칙대로 글을 쓴다.
  이때도 참고한 자료 링크를 본문에 언급하지 않고, 가장 대표적인 공식 출처 하나를
  `source.url`에 남긴다(`source.type`은 보통 `article` 또는 `blog`).
- **글 분량은 워드 문서 한 편 수준으로 상세하게 쓴다.** 소제목 몇 개에 문단 하나씩
  얹는 정도로 얕게 쓰지 않는다. 특히 실습형·증적형 글은 단계별 절차, 설정값 예시,
  검증 방법, 장애 대응, 체크리스트까지 빠짐없이 담아 실제로 그대로 따라 할 수 있는
  수준으로 작성한다. 이 원칙은 `증적` 태그가 붙은 글뿐 아니라 앞으로 쓰는 모든 글에
  적용한다.
- **본문이 길어지는 구간은 `<details><summary>` 토글로 접어서 정리한다.** `<h2>`는
  전체 흐름이 한눈에 보이도록 펼쳐진 상태로 두고, 그 아래 상세 절차·체크리스트·
  캡처 모음·시나리오별 세부 설명처럼 "필요한 사람만 펼쳐 보면 되는" 내용을 토글
  안에 넣는다. `assets/style.css`에 `.article-content details/summary` 스타일이
  이미 정의되어 있으니 그대로 사용하면 된다. 예시:
  ```html
  <details>
  <summary>실습 캡처 — ○○ 화면 모음 (n장)</summary>
  <img src="assets/img/.../capture-01.png" alt="..." loading="lazy">
  <p class="img-caption">... (실습 환경 캡처)</p>
  </details>
  ```
  이 원칙도 `증적` 태그 여부와 무관하게 앞으로 쓰는 모든 글에 적용한다.
- **`증적` 태그 글은 사진을 많이, 원본 워드 문서 내용의 거의 대부분을 담는다.**
  워드 파일에 캡처가 20장 넘게 있다면 그중 몇 장만 골라 쓰지 않고, 중복이 심한
  경우가 아니면 거의 전부를 STEP별로 토글에 나눠 넣는다(위 이미지 규칙·워딩 규칙은
  그대로 지킨다). pandoc 등으로 문서를 추출하면 이미지 파일명(`image1.png`,
  `image2.png`...)이 원본 문서의 캡처 번호·순서와 일치하지 않을 수 있으므로, 문서의
  캡션 번호를 그대로 믿지 말고 이미지 하나하나를 직접 열어 보고 실제 화면 내용에
  맞는 캡션을 새로 쓴다.

## 여러 PC로 나눠 작업하기

이 저장소는 여러 PC(노트북/데스크탑)에서 번갈아 작업합니다. **최신 여부 확인은
기본적으로 위 "버전 표시" 섹션의 `site.version` 숫자로 합니다** — 작업을 새로
시작하기 전에 항상 GitHub의 실제 최신 상태를 먼저 확인하고, 지금 들고 있는 로컬
사본의 버전이 그보다 낮으면 먼저 최신 내용을 받아온 뒤 이어서 작업합니다. PC마다
`git config user.name`을 따로 지정해야 하는 건 아니고(원한다면 `git log -1`로
마지막 커밋이 어디서 왔는지 보조적으로 확인할 수는 있지만 필수는 아님), 버전
숫자 하나로 충분합니다. `git push`는 이 저장소를 다루는 자동화 도구가 아니라 항상
사용자가 본인 PC의 실제 터미널에서 직접 실행합니다.

## 앞으로: 링크 자동 업로드 (설계 메모)

목표: 블로그·유튜브·기사·노션 링크를 주면 자동으로 요약·정리해 글로 올리기.
지금 구조가 그 토대입니다.

1. 링크 수집 → 본문/자막/메타 추출
   - 유튜브: 제목·설명·자막, 기사/블로그: 본문, 노션: 공개 페이지 내용
2. 요약·정리 → `content`(HTML), `summary`, `tags`, `category` 생성
   - 앞서 만든 회의극 파이프라인(또는 간단한 LLM 호출)으로 자동 생성 가능
3. `add_post.py` 의 `add_post(...)` 함수 호출 → `index.js` + `posts/<id>.js` 갱신
4. `git commit && git push` → GitHub Pages 자동 반영
   - GitHub Actions로 "새 링크가 담긴 파일이 올라오면 → 요약 → add_post → 커밋"
     워크플로를 붙이면 완전 자동화됩니다.

`source.type` 과 `source.url` 을 저장하므로, 각 글 하단에 "원문 보기" 링크가
자동으로 붙어 출처가 항상 남습니다.

## 검색 / SEO

- **사이트 내 검색**: 상단 검색창이 제목·요약·태그·카테고리명을 실시간 필터링(본문 전체
  검색은 하지 않습니다 — 이유는 위 "데이터 구조" 참고)
- **카테고리 + 태그**: 상단 카테고리 버튼, 태그 클라우드로 트리 탐색
- **검색엔진 노출**: 각 글에 `<meta description>` 와 구조화 데이터(JSON-LD `BlogPosting`)를
  주입해 구글이 제목·날짜·카테고리·키워드를 이해합니다
- 더 강한 SEO가 필요하면 글마다 정적 HTML을 생성하는 빌드 스텝과 `sitemap.xml` 을
  추가하면 됩니다(원하시면 만들어 드립니다).
